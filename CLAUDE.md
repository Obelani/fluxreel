# FluxReel

Clone rebrandizado do site ViralIA (ferramenta de geração de vídeos virais por IA). Front estático — HTML/CSS/JS vanilla, sem framework, sem build step. Hospedado na Vercel, deploy automático a cada push no GitHub. Desde a adição do backend de geração de vídeos, o projeto também tem `/api` (Vercel Functions em Node) — ver seção **Backend** abaixo.

## Arquivos (front)

- `index.html` — landing page pública. Hero, seção "estilos" (marquee com vídeos), carrossel "A gente entrega views" (imagens estáticas), monetização, depoimentos, "como funciona", FAQ. Botão "Entrar com Google" no cabeçalho.
- `login.html` — tela de login/cadastro (abas Entrar/Criar conta), botão Google + formulário e-mail/senha. Lê `?mode=signup` (abre direto na aba de cadastro) e `?next=` (pra onde voltar depois de logar).
- `create-series.html` — assistente de criação de série em 7 etapas (Nicho → Idioma e voz → Música de fundo → Estilo visual → Estilo de legenda → Efeitos → Detalhes da série) + popup de planos/pagamento no final. O paywall chama `/api/create-series` e `/api/create-checkout-session` de verdade (Stripe Checkout); depois do pagamento confirmado, chama `/api/generate-video` e acompanha o progresso via Supabase Realtime (modal de geração com barra de progresso, player quando ficar pronto). Exige login: redireciona pra `login.html` se não houver sessão (via `requireAuth()`). Quem já tem pelo menos 1 série cai direto no `dashboard.html` (exceto voltando de checkout `?success=1` ou pedindo `?new=1` explicitamente).
- `dashboard.html` — painel logado: cards de resumo (plano atual, créditos, botão "Gerenciar assinatura" via Stripe Customer Portal) + abas Séries / Vídeos / Guias / Fale conosco / Configurações (troca via JS, mesmo padrão de `wizard-step` do `create-series.html`). Séries e vídeos são lidos **direto do Supabase no client** (`supabase.from('series'/'videos').select('*')`) — RLS já restringe à própria linha do usuário, sem precisar de endpoint novo. Botão "Gerar vídeo" por série reaproveita `/api/generate-video` + o mesmo modal de progresso/Realtime do wizard.
- `auth.js` — toda a lógica de autenticação via Supabase (Google OAuth + e-mail/senha) e a proteção de páginas (`requireAuth()`). **Contém chaves reais** (Project URL e anon key do Supabase, nas 2 primeiras linhas com valor). Não são secretas (a `service_role key` que seria, e essa nunca é usada aqui), mas são configuração de produção — nunca sobrescreva essas duas linhas com placeholder.
- `logo-icon.webp` — ícone da marca.
- `LEIA-ME.txt` — lista de assets (imagens/vídeos/áudios) que ainda faltam subir pro site funcionar 100% (com os caminhos exatos esperados pelo código).

## Backend (`/api`, Vercel Functions)

Não muda as convenções do front (continua sem build step, sem framework) — é uma pasta `/api` à parte, com seu próprio `package.json` na raiz (dependências Node: `stripe`, `@supabase/supabase-js`, `@anthropic-ai/sdk`, `@upstash/qstash`, `ffmpeg-static`).

**Pagamento e créditos:**
- `api/_lib/supabaseAdmin.js` — client Supabase server-side, usa a `service_role key` (nunca exposta ao front).
- `api/_lib/auth.js` — `getAuthenticatedUser(req)`, valida o token Bearer (sessão Supabase) mandado pelo front e resolve o usuário. Toda function autenticada usa isso — nunca confiar em `user_id` vindo do client.
- `api/_lib/plans.js` — espelha os 3 planos definidos em `create-series.html` (`var PLANS`): mapeia plano+ciclo pro Price ID da Stripe e calcula quantos créditos cada ciclo de assinatura libera. Também guarda `CAKTO_OFFERS` (id da oferta da Cakto → plano/ciclo).
- `api/create-series.js` — salva a config do wizard (tabela `series`) assim que a etapa 7 termina, antes do paywall.
- `api/cakto-webhook.js` — webhook da **Cakto** (gateway de pagamento atual; a Stripe foi substituída). Valida a origem (HMAC `X-Cakto-Signature` com `CAKTO_WEBHOOK_SECRET`, fallback no campo `secret`), é idempotente (`claim_webhook_event` por evento+pedido) e trata: `purchase_approved`/`subscription_renewed` (upsert em `subscriptions` + `grant_subscription_credits`, chave por assinatura+período pra não creditar 2x o mesmo ciclo), `refund_requested`/`refund`/`chargeback` (`revoke_credits_for_refund`; o crédito do pagamento é retirado já no PEDIDO de reembolso, e a efetivação depois não reverte de novo porque `refund_requested` e `refund` usam a mesma chave `cakto:refund:<pedido>`; se o comprador desistir do reembolso os créditos NÃO voltam sozinhos — devolver manualmente com `grant_subscription_credits` e chave nova; pré-chargeback só loga), e `subscription_canceled/late/paused/resumed` (só status). O comprador é identificado pelo `?callback=<id do usuário>` no link do checkout (fallback: e-mail). Ofertas desconhecidas (outros produtos da conta) são ignoradas. A Cakto NÃO reenvia sozinha em resposta não-2xx: eventos que falharam se reprocessam pelo "Reenviar evento" no painel dela.
- `api/stripe-webhook.js` — recebe os eventos da Stripe, confirma pagamento e credita a conta do usuário (`grant_subscription_credits`, idempotente — protegido contra reentrega atrasada de evento, ver commit `f4345c0`). Também trata troca de plano: cancela a assinatura anterior só depois de confirmar a nova. **Legado**: a Stripe não é mais usada pra novas compras; o endpoint fica só pra assinantes antigos até migrarem.
- `api/subscription-status.js` — devolve a assinatura ativa do usuário (usado pelo paywall pra mostrar "seu plano atual"/"trocar de plano", e pelo dashboard).
- Checkout: não há mais function de checkout — o front manda direto pro link `https://pay.cakto.com.br/<oferta>?callback=<user id>` (mapa `CAKTO_OFFERS` em `create-series.html`, `dashboard.html` e `api/_lib/plans.js` — manter os três iguais). Antes de ir, dispara `AddToCart` (via `fbq`, que o tracker carrega) e grava `funnel_events.checkout_started`; a navegação é um clique programático num `<a data-sentinel-checkout>` pro tracker decorar o link. Seletor de quantidade de séries está escondido (ofertas têm preço fixo). "Gerenciar assinatura" abre `assinatura.cakto.com.br`. Página de Obrigado do produto na Cakto = `https://www.fluxreel.app/create-series.html?success=1` (o wizard espera o crédito chegar pelo webhook e gera o 1º vídeo). **Atribuição (UTMs do Facebook):** `attribution.js` (carregado em index/login/create-series/dashboard) guarda `utm_*`/`src`/`sck`/`fbclid` no localStorage assim que o visitante chega (última origem vale, 30 dias) e também no cadastro (`user_metadata.attribution`, pra sobreviver a e-mail de confirmação aberto em outro navegador); `goToCaktoCheckout` anexa esses parâmetros ao link da Cakto, que só lê `src`, `sck` e `utm_*` da URL do checkout. O admin mostra a origem de cada usuário. Anúncio do Facebook deve apontar pra landing (`https://www.fluxreel.app/`) com os parâmetros de URL do anúncio. **Tracking avançado:** o script `sentinel` (`https://track.fluxreel.app/api/t/tracker.js?tid=...`, antes do `</head>` em index/login/create-series/dashboard; NÃO no admin) substituiu o snippet manual do Pixel da Meta — o próprio tracker carrega o `fbq` do pixel mapeado pro host (`fluxreel.app` → `1783104722724738`), espelha PageView/InitiateCheckout com `eventID` (deduplica com o servidor), guarda UTMs em cookie `_stl_*` e **reescreve `utm_term` do link do checkout por `stl_<sessão>`** (é a chave que casa a venda com a visita — por isso o `attribution.js` ignora valores `stl_`). NÃO recolocar o snippet do Pixel: duplicaria PageView. Com Do-Not-Track o tracker se desliga por completo.
- **Suporte e WhatsApp do lead:** `support.js` guarda o número do suporte (`PHONE`, hoje 5535991747115) e injeta a barra fixa "Ficou com dúvida? Chame no WhatsApp" só no mobile (≤768px; fica abaixo dos modais e o toast sobe pra não cobrir). A barra existe SÓ na landing (`index.html`, aparece sempre) e no wizard (`create-series.html`, em modo `FLUX_SUPPORT_BAR='manual'`: só aparece se `/api/subscription-status` não trouxer assinatura ativa); login e dashboard não carregam o script — assinante já tem o menu Fale Conosco. Trocar o número = `PHONE` em `support.js` + o link estático `btn-whatsapp-contact` em `dashboard.html`. `whatsapp.js` normaliza/mascara o número (salvo em `user_metadata.whatsapp`, só dígitos com 55) e traz `FluxWhatsApp.ensure()`: o modal de coleta — pedido LOGO APÓS O LOGIN (wizard: título "Antes de começar", antes do passo 1; dashboard: "Antes de continuar"; não pergunta na volta do checkout) e, como rede de segurança, de novo no último passo do wizard e no "Gerar vídeo" do dashboard ("Último passo para gerar seu vídeo" — já salvo = não abre); sem opção de pular; checa o dado fresco no servidor (`auth.getUser`). Quem cria conta pelo formulário informa o WhatsApp no cadastro (campo obrigatório em `login.html`, gravado via `signUpWithEmail(..., whatsapp)`).
- **Admin — leads e APIs:** a lista de usuários mostra WhatsApp (link `wa.me`), filtro (com/sem WhatsApp, Google, formulário) e "Baixar leads (CSV)". A aba "APIs e saldos" chama `GET /api/admin?view=providers` (mesma function, pra não passar do limite de 12): só ElevenLabs (`/v1/user/subscription`, a chave precisa da permissão User/leitura) e fal.ai (`/v1/account/billing?expand=credits`, exige chave ADMIN — salvar como `FAL_ADMIN_KEY` na Vercel) têm saldo por API; Anthropic, Groq e QStash NÃO têm, então só mostram atalho pro console.

**Pipeline de geração do vídeo** (roteiro → imagens → narração → legendas → render), orquestrado via Upstash QStash — cada etapa processa e entrega a próxima pro QStash, que garante a entrega com retry se algo falhar:
- `api/generate-video.js` — debita 1 crédito (atômico), cria a linha em `videos`, dispara a 1ª etapa (`pipeline/script`). Devolve o crédito automaticamente se o pipeline falhar em qualquer etapa.
- `api/_lib/qstash.js` — publica a próxima etapa e verifica a assinatura das requisições recebidas do QStash.
- `api/_lib/pipelineStage.js` — helpers comuns a toda etapa: ler/verificar payload do QStash, marcar vídeo como falho + devolver crédito.
- `api/_lib/pipelineConfig.js` — mapeamentos entre o que o wizard oferece e o que cada API externa espera: duração → nº de cenas, duração → orçamento de palavras narradas (`WORD_BUDGET_BY_DURATION`), voz → `voice_id` da ElevenLabs, estilo de legenda → cores do texto queimado (`CAPTION_STYLES`) e fonte escolhida → arquivo(s) `.ttf` em `/fonts` (`CAPTION_FONTS`, 5 opções: Montserrat, Anton, Bebas Neue, Poppins, Oswald). Estilo **visual** (das imagens) não mora mais aqui — ver `visualStyles.js` abaixo.
- `api/_lib/visualStyles.js` — catálogo centralizado dos 14 estilos visuais oferecidos no wizard (Comic, Creepy Comic, Modern Cartoon, Disney, Mythology, Pixel Art, Stickmans, Ghibli, Anime, Painting, Dark Fantasy, Lego, Realism, Fantastic). Cada um tem `id`, `label` (nome exibido) e um prompt completo + regras negativas específicas — únicos lugares onde esse texto existe, nada disso é duplicado em outro arquivo. Disney/Ghibli/Lego mostram esse nome na interface, mas o prompt de verdade é neutro (não cita as marcas). Fallback explícito pra estilo inválido/ausente: `modern-cartoon` (nunca escolhe outro silenciosamente).
- `api/_lib/imagePrompt.js` — monta o prompt final de cada cena (`buildImagePrompt`), **em inglês**, nesta ordem: prompt completo do estilo (`visualStyles.js`) primeiro → bloco de formato/cena/personagens/universo + regras universais de consistência → prompt negativo universal → regras negativas do estilo. `validateImagePromptInput` roda antes de cada chamada à API de imagem. A fal.ai/z-image/turbo (modelo usado aqui) **não tem campo de `negative_prompt` nem aceita imagem de referência** — só `seed` é suportado de verdade (confirmado na doc da API), por isso o "negativo" é só texto dentro do mesmo prompt. Primeira versão tinha os prompts em português e o estilo no fim do texto — testado em produção e saiu ruim (Stickmans/Disney saindo foto-realistas): o modelo de imagem entende inglês bem melhor, e colocar o estilo logo no início evita que a instrução seja "diluída" num prompt longo.
- `api/pipeline/script.js` — roteiro cena a cena via Claude Sonnet 5 (tool use, JSON estruturado). Além de `title`/`scenes`, o schema agora força o Claude a definir `environment` (descrição fixa do universo) e `characters` (ficha visual de cada personagem recorrente, `{id, description}`) **uma única vez por vídeo**, e cada cena lista `charactersInScene` (quem aparece nela) — existe pra `images.js` reaproveitar a mesma ficha em toda cena, em vez do modelo "inventar" o personagem de novo a cada imagem (causa original da inconsistência visual entre cenas do mesmo vídeo).
- `api/pipeline/images.js` — uma imagem por cena via fal.ai (`fal-ai/z-image/turbo`); o prompt de cada uma vem de `buildImagePrompt()` (não monta texto na mão aqui). Usa a mesma `seed` (derivada deterministicamente do `video_id`) em todas as cenas do vídeo — único recurso de continuidade visual que essa API realmente suporta.
- `api/pipeline/narration.js` — narração completa via ElevenLabs (`api/_lib/elevenlabs.js`), guardada no Supabase Storage (bucket `media`, público).
- `api/pipeline/captions.js` — transcrição com timestamp por palavra via Groq Whisper (`api/_lib/groqWhisper.js`, `whisper-large-v3-turbo`). Também é onde a duração REAL do vídeo é validada contra a faixa escolhida no wizard (`DURATION_BUCKET_SECONDS`) — diferente do orçamento de palavras do roteiro (`WORD_BUDGET_BY_DURATION`, só uma estimativa prévia), aqui é o fato consumado: se a narração medida estourar o topo da faixa (+15% de tolerância), pede pro Claude reescrever só a narração mais curta (mantendo cena/visual/personagens/universo — as imagens já geradas continuam válidas) e regenera áudio+transcrição uma vez.
- `api/pipeline/render.js` — monta o MP4 final direto com **ffmpeg puro** (`ffmpeg-static`, sem API externa nem serviço à parte): slideshow das imagens com duração por cena (concat demuxer), narração + música misturadas, legenda queimada via arquivo `.ass` (palavra atual em destaque, resto apagado — mesmas cores/fonte do preview do wizard; fundo colorido dos estilos `bold-yellow`/`blackbox` é aproximado com contorno, não é pílula de verdade ainda). Sobe o resultado pro Supabase Storage e marca `ready`/`failed` ele mesmo, tudo dentro da mesma function. Roda até 300s (precisa de **Fluid Compute habilitado** no projeto da Vercel + `maxDuration: 300` em `vercel.json`, bem acima do padrão de 10-60s). Chegou nessa forma depois de tentar Creatomate (caro) e Revideo self-hosted no Fly.io (instável — Chromium headless crashando sob carga, múltiplas causas de erro diferentes) — ffmpeg direto é mais simples, mais estável e sem custo de API, batendo com o próprio pipeline de custos do ViralIA (que não lista nenhuma API de render).

**Banco e config:**
- `supabase/schema.sql` — schema completo (tabelas `series`, `subscriptions`, `credit_balances`, `credit_ledger`, `videos` + RLS + funções atômicas de crédito). Aplicado manualmente no SQL Editor do Supabase; não há CLI/migrations configurado.
- `.env.example` — lista todas as variáveis de ambiente que o backend precisa. Copiar os valores reais só pra Vercel (Settings > Environment Variables), nunca commitar um `.env` de verdade.

Créditos: 1 crédito = 1 vídeo. Pacote fechado por ciclo de cobrança (não recarrega diariamente) — fórmula e valores em `api/_lib/plans.js`.

`scripts/test-visual-styles.js` — testes do catálogo de estilos visuais e da montagem de prompt (`node scripts/test-visual-styles.js`, só `node:assert`, sem framework/dependência nova). Não chama nenhuma API externa, só testa o texto montado por `buildImagePrompt()`.

Existe uma skill em `~/.claude/skills/backend-foundations/` (nível de usuário, disponível em qualquer projeto) que audita/implementa os padrões genéricos usados aqui (autenticação, higiene de segredo, checklist de domínio, confiabilidade de webhook, saldo atômico, troca de plano) — invocável via `/backend-foundations`.

## Convenções

- CSS 100% próprio, sem Tailwind nem outro framework — variáveis CSS (`:root`) para os tokens de marca, classes utilitárias próprias (`.btn`, `.btn-gradient`, `.field`, etc.).
- JS vanilla, estilo `function`/`var` (compatibilidade ampla), sem bibliotecas além do `supabase-js` (carregado via CDN jsdelivr).
- Todo texto de interface em português (pt-BR).
- Cada página HTML é autocontida — CSS e JS inline no próprio arquivo, sem arquivos `.css`/`.js` separados (exceto `auth.js`, que é compartilhado entre as páginas).
- Sem build step: qualquer alteração é direto no HTML/CSS/JS final, pronta pra deploy.

## Autenticação (Supabase)

- Login com Google e e-mail/senha via Supabase Auth.
- Google Cloud Console: projeto "fluxreel", OAuth Client tipo "Aplicativo da Web", origem autorizada = domínio canônico de produção (`https://www.fluxreel.app` — **com www**, é a variante que a Vercel serve direto; `fluxreel.app` sem www só redireciona 308 pra ela; o domínio antigo `www.fluxreel.com.br` segue ligado ao projeto durante a transição).
- Supabase → Authentication → URL Configuration: Site URL = `https://www.fluxreel.app`, Redirect URLs cobrindo `https://www.fluxreel.app/**`. Qualquer webhook externo (ex.: Stripe) também precisa usar o domínio com www — o sem-www não é seguido por chamadas servidor-pra-servidor.
- `REDIRECT_AFTER_LOGIN` em `auth.js` aponta pra `/create-series.html`.
- `requireAuth()` (em `auth.js`) é a função que protege páginas — chame no topo de qualquer página nova que deva exigir login.
